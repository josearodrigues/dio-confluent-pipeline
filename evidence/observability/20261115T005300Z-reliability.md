- Coletado em (UTC): 20261115T005300Z

- Pipeline: PostgreSQL (Neon) → Debezium CDC V2 → Kafka Topics (Avro) → Flink SQL (Temporal Join + CEP) → PostgreSQL Sink → public.fraud_alerts

---

## 1. Matriz de Garantias Trecho a Trecho

| Trecho do Pipeline | Garantia Técnica | Mecanismo de Proteção | Comportamento em Caso de Falha / Recuperação |
|---|---|---|---|
| **PostgreSQL Origem** | **ACID / Durabilidade** | Write-Ahead Logging (WAL) com `wal_level = logical` | Transações atômicas persistidas no disco. O PostgreSQL garante integridade referencial e retenção de logs enquanto o slot de replicação estiver ativo. |
| **PostgreSQL → CDC Debezium** | **At-least-once** | PostgreSQL Replication Slot (`payments_slot`) com plugin `pgoutput` e `REPLICA IDENTITY FULL` | Se a tarefa CDC cair ou for reiniciada, o conector retoma a leitura a partir do último LSN confirmado no slot. Pode haver reemissão de eventos duplicados, mas nenhuma perda. |
| **CDC → Tópicos Kafka** | **At-least-once + Durabilidade 3x** | Confluent Cloud Kafka Basic com fator de replicação 3x em AWS `us-east-2`, ACKs do produtor e Schema Registry Avro | Mensagens são replicadas e distribuídas nos tópicos `payments.*`. O contrato Avro impede a publicação de dados malformados ou incompatíveis. |
| **Kafka → Flink SQL** | **Stateful Event-Time** | Flink SQL com `$rowtime` e Watermark progressivo (`SOURCE_WATERMARK()`) | Eventos fora de ordem são absorvidos pela tolerância temporal do Flink CEP (`MATCH_RECOGNIZE`). Chaves declaradas com `NOT ENFORCED` servem como metadados de particionamento. |
| **Flink SQL → Tópico fraud_alerts** | **Append Changelog** | Tópico de saída gerenciado no cluster Kafka | Flink emite alertas consolidados com as métricas do padrão (`first_txn`, `last_txn`, `txn_count = 3`). |
| **Tópico fraud_alerts → Consumidor / Sink**<br>*(O ELO FRACO)* | **At-least-once**<br>*(Risco de Duplicidade)* | Consumer Groups (`connect-lcc-1260x85` / `app-reader`) com commit de offset | **O Elo Fraco do Pipeline:** Em sistemas de streaming, rebalanceamentos de grupo de consumidor ou reinício de tarefas consumidoras podem reler mensagens a partir do último offset commitado, entregando a mesma notificação mais de uma vez. |
| **Consumidor → Efeito Final no Banco**<br>*(Resolução do Elo Fraco)* | **Idempotência (Efeito Exactly-Once)** | PostgreSQL Sink gerenciado configurado com `insert.mode = UPSERT` e Primary Key composta `(card_id, first_txn)` | **"Idempotência é código meu":** Mesmo que o Kafka entregue a mesma notificação repetidas vezes após um rebalanceamento, o conector executa uma atualização atômica (`ON CONFLICT DO UPDATE`) sobre a chave `(card_id, first_txn)` na tabela `public.fraud_alerts`, impedindo duplicidade no banco de dados relacional. |

## 2. Análise Crítica de Performance, Custo e Volume no CDC

### O Desafio da Leitura Serial do WAL (`tasks.max = 1`)
- O conector PostgreSQL CDC é arquiteturalmente restrito a `tasks.max = 1` porque uma conexão de replicação lógica no PostgreSQL vincula-se de forma exclusiva a um único `replication slot`.
- No nosso laboratório, a carga de **2.760 registros determinísticos** (200 customers, 240 accounts, 320 cards e 2.000 transactions) levou cerca de 30 a 40 minutos para concluir o snapshot inicial, serialização Avro e registro nos 4 tópicos do Schema Registry.

### Impacto de Escala e Custo em Ambientes Produtivos
1. **Retenção de WAL e Disco no Banco:** Em bancos com milhões de transações, um snapshot serial longo força o PostgreSQL a acumular arquivos WAL no disco até que o conector confirme o LSN. Se a taxa de geração de log for superior à taxa de ingestão do conector, o disco do banco pode atingir 100% de capacidade.
2. **Custo de Conectores Gerenciados:** Conectores gerenciados na nuvem cobram por hora de tarefa ativa (US$ 0,50/hora por tarefa). Um snapshot de milhões de registros que demore 20 ou 30 horas gera um custo financeiro direto relevante apenas na fase preparatória.
3. **Estratégias de Mitigação Recomendadas:**
   - **Ingestão Paralela por Partição (Chunked Snapshot):** Particionar tabelas históricas de transações e utilizar múltiplos conectores com slots independentes para paralelizar a carga inicial.
   - **Bootstrap via Objeto (Data Lake / S3 / GCS):** Realizar a carga pesada inicial através de exportação em lote (*batch dump* em Parquet) diretamente para o data lake/tabela destino, iniciando o conector CDC com `snapshot.mode = never` ou `custom` a partir do LSN exato do corte do dump.

## 3. Síntese para a Avaliação da DIO

- **Elo Fraco Identificado:** A entrega Kafka → Consumidor é *at-least-once*, sujeita a duplicatas por rebalanceamento ou restart.
- **Solução Implementada no Projeto:** Idempotência ponta a ponta no PostgreSQL Sink via `insert.mode = UPSERT` e PK `(card_id, first_txn)`.
- **Garantia Efetiva Comprovada:** O pipeline atinge o comportamento **Exactly-Once semântico no destino relacional**, mesmo operando com transporte *at-least-once*.
